# vidlink 配额消耗系数表（倍率表）

本文解释 vidlink 每一次调用到底消耗多少配额，以及每个数字为什么是它。
所有数值都来自代码里的唯一来源：`internal/quota/quota.go` 的 `DefaultTable()`。
改动配额策略**只改那一处**，本文随之同步。

---

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| **配额（quota）** | 一个账号可用量的上限，由管理员分配。**不是余额、不是货币，不与任何支付行为挂钩。** 它是资源的用量额度，类似"每月 1000 次调用"。 |
| **端点（endpoint）** | 四类业务接口：`info` / `links` / `detail` / `batch_links` |
| **平台（platform）** | `douyin` / `bilibili` / `kuaishou` / `xiaohongshu` |
| **端点系数** | 这个接口本身消耗多少（"卖什么"） |
| **平台系数** | 这家上游更贵多少（"哪家贵"） |
| **账号倍率** | 给这个账号的额外缩放，管理员设置（"给谁调"） |

代码里的字段名一律用单位无关的 `quota` / `used` / `cost`，
"配额"只是文案里出现的名字（`internal/server/handlers.go` 的 `unitName`）。
将来要改名（配额 → 积分 → 品牌名）只改那一个常量，不动 API 契约。

---

## 2. 计量公式

```
一次调用的消耗 = 端点系数(端点, 平台) × 条数 × 账号倍率
```

- **端点系数** = 端点基准 × 平台系数。两者都固化在 `DefaultTable()` 里。
- **条数**：只有批量端点大于 1；其余端点恒为 1。
- **账号倍率**：该账号的 `multiplier` 字段，默认 `1.0`。

结果**保留 4 位小数**（用整数运算四舍五入，避免账本里累积出
`0.30000000000000004` 这种浮点垃圾）。

## 3. 端点系数

| 端点 | 方法 | 通用档 | 抖音 | 返回内容 |
| --- | --- | --- | --- | --- |
| `info` | `GET /v1/info` | **0.5** | **0.75** | 仅元信息 + 可用档位列表，**不含任何直链** |
| `links` | `GET /v1/links` | **1.0** | **1.1** | 仅直链，**不含元信息** |
| `detail` | `GET /v1/detail` | **1.2** | **1.5** | 元信息 + 全部档位直链 + 字幕/图集 |
| `batch_links` | `POST /v1/batch/links` | **0.75 / 条** | **不支持** | 批量只取直链，按**成功条数**计量 |

"通用档"= 表里没单独列出的平台都走它（快手、小红书、B 站）。

### 3.1 为什么 `info` 只有 0.5

它不提供任何可播放资源，客户拿到后必然要再调一次 `links` 才能用。
如果 `info` 和 `links` 同价，客户会为了省钱直接用 `links`，
`info` 这个端点就没有存在意义了。0.5 让"先看有哪些档位再决定要不要取流"这件事足够便宜。

### 3.2 为什么 `detail` 是 1.2 而不是 1.5

`detail` 的内容等于 `info` + `links` 的并集：`0.5 + 1.0 = 1.5`。
打包价 1.2 相当于**八折**（1.2 / 1.5 = 0.8）。
两个必须同时成立的不变量：

1. `detail > links`（1.2 > 1.0）——否则 `links` 被 `detail` 完全支配，没人会单独调 `links`；
2. `detail < info + links`（1.2 < 1.5）——否则打包没有意义，客户不如分两次调。

这两条都有测试锁住（`TestDetailCoefficientExceedsLinks`、`TestDetailHasBundleDiscount`）。

### 3.3 为什么批量是 0.75 而不是 1.0

批量比单条 `links` 便宜 25%（0.75 / 1.0）。代价交换是明确的：

- 客户省配额，但要接受一次调用只拿直链、且条数有下限（默认 5，上限 20）；
- 我们省上游——10 条合并成一次调用，比 10 次独立请求少 9 次鉴权、少 9 个连接、少 9 次对上游的冲击。

下限设成 5 而不是 1 是刻意的：否则客户拿 1 条也能享受 25% 折扣，折扣就失去引导合并的意义。

## 4. 平台系数

只有抖音单独上浮，B 站/快手/小红书一律走通用档。

### 4.1 抖音：`info 0.75` / `links 1.1` / `detail 1.5`

三条实测依据（2026-09 实网测定）：

1. **信息查询与取流是同一条上游请求。** 抖音不像 B 站能只调 `view` 接口拿元信息——
   拿元信息和拿直链都要走同一条签名 `detail` 请求（`a_bogus` + `x-secsdk-web-signature` + `timestamp`）。
   所以 `info` 档位的上游成本并不比 `links` 低多少，这也是它上浮幅度最大（+50%）的原因。
2. **它在 IP 维度限流，是最容易触发风控的一家。** 实测约 60 次请求 / 20 线程后开始降级，
   表现为 HTTP 200 但**响应体 0 字节**，恢复期约 20 分钟；换新身份**不能**绕过（真实浏览器同样被拦）。
   成本不只是"多打一次上游"，还包括被限流后整台机器的解析能力下降。
3. 上浮后仍低于"两次调用"的价格，客户用 `detail` 一次拿全是更划算的选择。

### 4.2 B 站：不单独定价

实网验证：**匿名即可拿到完整 1080P**——走非签名 `x/player/playurl` 通道并带 `try_look=1`，
6/6 复现；`ffprobe` 量到 212.32 秒，与官方时长 213 秒一致，是完整视频不是试看片段；
CDN 直链无需 Cookie、无需 Referer、无特定 UA 要求（HTTP 206 正常）。

也就是说 B 站没有任何额外成本，也没有内嵌账号（URL 里 `mid=0`）。
既然不额外花钱，就没有理由对客户额外收配额，因此与通用档一致。

> 顺带说明：B 站视频**画面内的强制水印**无法去除，这是平台侧烧进画面的，
> 业界普遍如此，与本服务的能力边界无关。

### 4.3 批量不支持抖音

抖音进批量会**瞬间打出多个请求**，在 IP 维度限流下等于自残——
一次 20 条的批量足以把整台机器打进 20 分钟的降级期。

因此批量端点对抖音返回明确原因而不是"倍率未定义"：

```json
"batch_links": {
  "unsupported": true,
  "reason": "抖音按 IP 维度限流，批量会瞬间打出多个请求，容易被判定为异常流量。请改用 GET /v1/links 逐条获取"
}
```

### 4.4 新增平台怎么办

表里**只列与通用档不同**的平台。新增一个平台时不需要动这张表，
它会自动走通用档，有一个合理的默认值；只有确认它的上游成本明显不同，才在表里加一行。

## 5. 账号倍率

由管理员通过 `PATCH /v1/admin/accounts/{key}` 的 `multiplier` 字段设置，默认 `1.0`。

| 倍率 | 效果 | 典型用途 |
| --- | --- | --- |
| `0` | **不消耗配额**，但仍累计 `calls` 与 `used` 统计 | 内部自用账号、联调账号 |
| `0.5` | 消耗减半 | 活动期、友情账号 |
| `1.0` | 标准 | 默认值 |
| `2.0` | 消耗翻倍 | 内部结算、限制高消耗客户 |

要点：

- 倍率是**账号级**的，与端点/平台系数相乘，不覆盖它们；
- 倍率为 `0` 不等于"无限制"：账号仍需有可用配额，只是每次消耗 0，**调用次数照记**，
  所以用量报表不会因为倍率为 0 就变成盲区（`TestZeroQuotaAccountIsUnmeteredButCounted`）；
- 倍率为负会被当成 `0` 处理；
- 新建账号的默认倍率是 `1.0` 而不是 `0`——`0` 是"免费"这样一个有意义的取值，
  不能当成"没填"的默认值（`handleAdminCreateAccount` 用指针区分"没提"与"显式 0"）。

## 7. 计算与结算规则

### 7.1 只在实际成功时扣减

上游超时、内容不存在、被限流、参数错误——**一律不扣**。
上游抖动不是客户的问题，算进用量会直接变成投诉。
批量接口按**成功的条数**结算，失败条目不计量（`TestBatchChargesOnlySuccess`）。

### 7.2 预授权：先按最贵档位检查

解析前我们还不知道链接属于哪家平台（要解析才知道），
但可以先按该端点**在所有平台中的最高系数**检查一次配额够不够
（`Table.MaxCoefficient`：`info` 0.75、`links` 1.1、`detail` 1.5、`batch_links` 0.75）。

- 目的：不让配额不足的账号白跑上游，也避免"结果已经返回了才发现配额不够"；
- 它**只是上限检查，不会多扣**——真正的扣减仍按解析出来的实际平台结算；
- 检查不通过返回 `429` + `kind: "quota_exhausted"`。

> 刻意**不使用 `402 Payment Required`**：那个状态码字面上就是"需要付款"，
> 会把一个"用量额度用完"的状态描述成商业交易。配额与金额无关，`429` 语义准确得多。

### 7.3 结算失败不影响已返回的结果

配额扣减本身出错时，客户端**仍然拿到 200 与正确的解析结果**，
服务端记 error 日志让运维介入。客户已经拿到的结果不能因为记账问题被改成 500。

### 7.4 响应头

| 头 | 含义 |
| --- | --- |
| `X-Quota-Consumed` | 本次调用消耗的配额 |
| `X-Quota-Remaining` | 该账号剩余可用配额 |

### 7.5 随时可自查

| 接口 | 说明 |
| --- | --- |
| `GET /v1/usage` | 自己账号的 `quota` / `used` / `calls` / `multiplier`，以及本人各平台的系数表 |
| `GET /v1/platforms` | 平台清单 + 各平台 `rates`（免费，无需配额） |
| `GET /v1/admin/quota` | 管理员可调整的系数全貌 |

账号对象里的 `quota` 是**剩余可用配额**（消耗会直接减它），
`used` 是**累计消耗**，`calls` 是**累计调用次数**（含倍率为 0 的调用）。

## 8. 算例

| 场景 | 计算 | 消耗 |
| --- | --- | --- |
| 快手 `links` | 1.0 × 1 × 1.0 | **1.0** |
| 抖音 `links` | 1.1 × 1 × 1.0 | **1.1** |
| 抖音 `info` | 0.75 × 1 × 1.0 | **0.75** |
| 小红书 `detail` | 1.2 × 1 × 1.0 | **1.2** |
| 抖音 `detail` | 1.5 × 1 × 1.0 | **1.5** |
| 抖音 `info` + `links`（分两次） | 0.75 + 1.1 | **1.85**（比 `detail` 的 1.5 贵） |
| 批量 10 条快手 | 0.75 × 10 × 1.0 | **7.5** |
| 批量 10 条快手，其中 3 条失败 | 0.75 × 7 × 1.0 | **5.25** |
| 抖音 `detail`，账号倍率 0.5 | 1.5 × 1 × 0.5 | **0.75** |
| 抖音 `detail`，账号倍率 0 | 1.5 × 1 × 0 | **0**（仍记 1 次调用） |
| 批量 20 条小红书，账号倍率 2.0 | 0.75 × 20 × 2.0 | **30** |

从最后几行可以看出账号倍率的作用：**它是唯一的单账号调节旋钮**，
不需要改共享的系数表就能给某个账号开活动或限流。

## 9. 怎么改

1. 改 `internal/quota/quota.go` 的 `DefaultTable()`——**唯一**的数值来源；
2. 跑 `go test ./internal/quota/` 确认不变量仍成立；
3. 若新增/删除端点或平台的组合，同步更新 `internal/server/handlers.go` 的 `allRates()`；
4. 更新本文第 3、4、6 节的表格；
5. `make check`（格式 + vet + 测试）。

被测试锁住的不变量（改表时不要破坏）：

| 不变量 | 测试 |
| --- | --- |
| `detail > links` | `TestDetailCoefficientExceedsLinks` |
| `detail < info + links`（打包有折扣） | `TestDetailHasBundleDiscount` |
| 批量不支持抖音，且给出原因 | `TestBatchRejectsDouyin` |
| 只按实际平台结算，不多扣 | `TestConsume` |
| 系数取 4 位小数、非负倍率 | `TestConsumeRounding`、`TestConsumeRejectsNegativeMultiplier` |
| 倍率 0 不扣配额但仍计次 | `TestZeroQuotaAccountIsUnmeteredButCounted` |

单账号的临时调整**不要**改这张表——用账号倍率。
表是共享的、影响所有客户；倍率是单账号的。

# 四平台视频解析调研报告

> 调研对象：抖音、哔哩哔哩、快手、小红书
> 调研方式：阅读 14 个开源仓库 + 官方/社区文档 + **真实接口实测验证**
> 所有"实测"结论均可在本机复现（见文末复现命令）

## 0. 先说三个会改变项目设计的结论

### 0.1 "去水印"的本质是**选择平台已发布的干净流**，不是图像处理

四个平台的媒体接口**都已经提供了不带水印的地址**，解析器要做的只是"选对字段"：

| 平台 | 带水印的字段 | 无水印的字段 |
|---|---|---|
| 抖音 | `video.download_addr`（URL 上带 `&watermark=1`） | `video.play_addr` |
| 快手 | 无此区分（`mainMvUrls[0].url` 本身就是干净的） | 同左 |
| 小红书 | 图片 `urlDefault` 带尺寸处理后缀 | 视频 `masterUrl`/`originVideoKey`；图片需改写 URL |
| B 站 | 无字段级区分，**与取流通道有关** | 见 0.2 |

**UP 主自己压进画面的水印是像素内容，任何解析器都无能为力。**
这一类"水印"和"平台下发的台标"是两回事，后者的确是可以通过换取流通道绕开的。

### 0.2 B 站的"水印"真相：不是参数问题，是通道问题

这是本次调研最有价值的发现之一。

> `BBDown -t <url>`：使用 TV 接口下载（粉丝量大的 UP 主片源通常**无水印**）
> —— BBDown 官方文档 `docs/wiki/Getting-Started.md:68-69`

对应的源码分支（`BBDown.Core/Parser.cs:49-50`）：

```csharp
string prefix = tvApi
    ? bangbang ? $"{TvHost}/pgc/player/api/playurltv" : $"{TvHost}/x/tv/playurl"
    : bangumi ? $"{Host}/pgc/player/web/v2/playurl" : $"{Host}/x/player/wbi/playurl";
// TvHost 默认 = api.snm0516.aisee.tv
```

此外，取流响应的 CDN URL 尾部确实带一个水印开关位掩码参数：

```
...&logo=80000000    ← 主流通道路径
...&logo=40000000    ← 另一路
logo=00000000        ← 音频流
```

社区文档对该参数**没有任何说明**，所以"`logo=` 控制水印下发"目前只能算**合理推断**，
需要 A/B 实测才能定论。但它与"TV 通道通常无水印"的社区共识方向一致。

**结论与决策**：B 站的高清无水印路线是「实现 TV 端 `x/tv/playurl`（需要 TV 端
`access_token` + `appkey` 签名）」。

> ⚠️ **本项目已决策放弃这条路线**。经确认"平台下发水印"在 B 站及整个行业
> 普遍存在，不值得为此引入 TV 端 `access_token` 依赖与额外维护成本。
> 本项目对 B 站**只做清晰度优先，不处理水印**。

本节保留完整技术记录，供后来者参考。

## 1. 抖音

### 1.1 链接形态

```
https://v.douyin.com/xxxxx/                    短链（需展开）
https://www.douyin.com/video/{aweme_id}        视频页
https://www.douyin.com/note/{aweme_id}         图文页
https://www.douyin.com/jingxuan?modal_id=xxx   精选页（ID 在 query）
https://www.iesdouyin.com/share/video/{id}     分享页 ← 本项目的关键
```

### 1.2 两条链路

**主链路（零签名、零 Cookie）** — 本项目采用

```
GET https://www.iesdouyin.com/share/video/{aweme_id}
  → HTML 中 window._ROUTER_DATA = {...}
  → loaderData[video_(id)/page].videoInfoRes.item_list[0]
```

这条路线的价值被严重低估：它的数据完整度足以支撑视频/图集解析，
而且**不需要 a_bogus、不需要 Cookie、不需要 ttwid**。稳定性远高于签名链路。

**增强链路（需签名 + Cookie）**

```
GET https://www.douyin.com/aweme/v1/web/aweme/detail/?<30+ 参数>&a_bogus=<sig>
  Headers: Referer: https://www.douyin.com/
  Cookie:  ttwid / msToken / s_v_web_id(UIFID_TEMP) 等
```

增强链路的唯一优势是能拿到 `video.bit_rate[]` 多档清晰度
（`gear_name` / `quality_type` / `play_addr.data_size`）。

### 1.3 签名：a_bogus

算法结构（纯计算，不需要 JS 引擎）：

```
1. paramsHash = SM3(SM3(query + "cus"))
2. methodHash = SM3(SM3(method + "cus"))
3. uaCode     = 32 字节指纹常量
4. 按固定模板拼出 payload（含时间戳、三个随机数、哈希片段）
5. checksum   = XOR(payload)
6. prefix     = 三个随机数的 12 字节编码
7. cipher     = RC4(key='y', payload)
8. result     = 自定义 Base64(prefix + cipher)
```

**本项目实测发现的矛盾（重要）**

社区参考实现（`wujunwei928/parse-video`，MIT）的源码与它自己给出的黄金向量
**互相矛盾**：

- 模板第 34 号标志位，在**密文**里必须是 `2`；
- 但**校验和**却要按 `3` 计算。

我们做了穷举验证：只有「密文用 2 + 校验和用 3」这一种组合能逐字节复现它的
黄金向量；照抄源码则差恰好 1 个字符。也就是说该参考实现的代码与它的测试
向量至少有一处是陈旧的，而离线无法判定哪个对。

**本项目的处理**（遵循"不要写死"原则）：

- 把这个标志位做成 `abogus.Variant` **数据**，两个解释都保留；
- 默认取 `VariantVectorFaithful`（以黄金向量为准，因为它是唯一外部证据）；
- 写测试把这个已知差异**固化**下来——一旦差异位置或数量变化，测试立刻报警；
- 指纹常量无法由 UA 推导（对 Chrome 80–135 + iPhone Safari UA、
  UTF-16 编码 / RC4(0,1,14) / 自定义 Base64 等十余种组合穷举均不匹配），
  因此也做成可替换的 `Fingerprint`，而不是散落的魔法数字。

### 1.4 无水解与清晰度

```go
// 无水印地址
item.video.play_addr.url_list[0]

// 带水印地址（其 URL 带 &watermark=1，仅在别处都拿不到时才兜底）
item.video.download_addr.url_list[0]

// 多档清晰度（仅 web detail 接口提供）
item.video.bit_rate[].{gear_name, quality_type, bit_rate, is_h265,
                       play_addr.{url_list, width, height, data_size}}
```

> 注意：早期广泛流传的 `playwm → play` 字符串替换技巧，
> 在当前的参考实现中已经**不再需要**（`grep playwm` 全仓库零命中）。
> 但分享页偶尔仍会返回 `playwm` 地址，因此本项目保留该替换作为兜底。

清晰度排序键（参考社区实现）：
`(max(height,width), FPS, bit_rate, data_size)`，取最大者。
**必须在 `play_addr` 族内排序，不要把 `download_addr` 混进去**——
它可能码率更高但带水印。

#### (4) 网页 JS 的真相：混合体，其中 bdms.js 是明文的

抖音的 JS 防护由**两块**组成，性质完全不同：

**(a) `byted_acrawler`（首页内联，71KB VM）—— 真·VM 混淆**

```
<script>var glb;(glb="undefined"==typeof window?global:window)._$jsvmprt=function(b,e,f){...
```

胶水层逻辑（明文可读）：

```js

var __ac_nonce = _f2("__ac_nonce"),
    __ac_signature = window.byted_acrawler.sign("", __ac_nonce);
```

**实测：这个 VM 可以在 Node 里直接执行**，只要提供最小 DOM 宿主：

```json

 "acrawlerKeys": ["BytedAcrawler","getReferer","init","sign"],
 "signature_nonce": "_02B4Z6wo00f01XFggJQAAIDCjp9.aHnh-CVxQoQAADcD19"

```

即 `__ac_signature` **不需要逆向**，执行即可得到。

**(b) `bdms.js`（外部加载，147KB）—— 明文压缩的 webpack bundle**

从 CDN 可以直接下载（实测多个镜像可用）：

```
https://lf-c-flwb.bytetos.com/obj/rc-client-security/web/stable/1.0.1.19-fix.01/bdms.js
https://lf3-cdn-tos.douyinstatic.com/obj/rc-client-security/web/stable/1.0.1.19-fix.01/bdms.js
```

文件开头是 `/* V 1.0.1.19-fix.01 */`，结构是标准 webpack 模块表 —— **不是混淆代码**。

它的职责（源码可读）：

```js
// 挂载到 window.bdms
e.d(n, { getReferer: function(){ return Or }, init: function(){ return hr } });
```

**实测：在 Node 里加载后 `window.bdms` 成功暴露 `init`/`getReferer`，
并且 `fetch` 被成功劫持**（`fetchReplaced: true`），
还会自动向身份铸造端点发请求：

```
XHR POST https://mssdk.bytedance.com/web/r/token?ms_appid=6383
body: {"magic":538969122,"version":1,"dataType":8,"strData":"fvz8/AIqwGyT6EqeesD0..."}
```

`strData` 就是 VM 生成的、用来换取 `msToken`/`UIFID` 的加密载荷。

其中的 VM 程序也能定位到（base64 → XOR → raw DEFLATE，解码逻辑在源码里明文可读）：

```js

  for (var r = atob(t), e = 0, n = 4; n < 8; ++n) e += r.charCodeAt(n);

```

（`_` 作为 `Array.from` 的 mapFn，key 是 `bytes[4..7] 之和 % 256`。）

#### (5) 结论：已打通（2026-09-14 复测）

上面 (1)~(4) 的分析**方向基本正确，但严重高估了难度**。复测后的结论是：

**抖音可以纯 Go 打通，不需要 Node sidecar，不需要 JS 引擎，不需要浏览器。**

关键是重新认识了几个签名件的性质：

| 签名件 | 性质 | 结论 |
|---|---|---|
| `a_bogus` | 纯算法（SM3+RC4+自定义 base64） | ✅ `internal/sign/abogus` 已实现，**且现网直接接受老一代实现** |
| `x-secsdk-web-signature` | **纯 MD5** + 写死在客户端的公开盐 | ✅ `internal/sign/secsdk` 已实现 |
| `timestamp` | `time.Now()` | ✅ |
| `UIFID_TEMP` | 服务端签发的访客标识 | ⚠️ 唯一必须外部取得的，但**一次铸造、长期复用** |

**当初的误判**：以为 `bdms.js`（JSVMP）是必经之路。实际上：

1. `bdms.js` 只负责 **`a_bogus`**，而 `a_bogus` 早已被纯算法复现。
   实测把本项目的 Go 实现直接拿去请求，**HTTP 200、返回完整作品数据**。
   （顺带验证：现网**同时接受**老一代"对 HTTP method 做哈希"的实现与
   新一代"不对 method 做哈希"的实现，签名长度分别为 164 / 192 字符。）
2. `x-secsdk-web-signature` 名字里有 "secsdk"、叫 "signature"，
   但它是 `md5(uifid_timestamp_SALT_query)`，**不含任何密钥**。
   它挡不住任何有心人——真实作用是「格式约束 + 减速带」。
   正因为盐是公开的，**真正的门只有 `UIFID_TEMP`**：签名覆盖了它，
   而它是服务端签发的，算不出来。
3. **`UIFID_TEMP` 的获取方式也已经找到**（原判断"由 bdms.js 铸造"是错的）：

```
① GET https://www.douyin.com/              -> 72KB 挑战页 + __ac_nonce
② node acrawler-sign.js <nonce> <页面>      -> __ac_signature（与 nonce 绑定）
③ 带 nonce + signature 再 GET 首页          -> Set-Cookie 下发 UIFID_TEMP + ttwid
```

第 ② 步需要执行页面内嵌的 `byted_acrawler` 虚拟机，但**它在 Node 里能直接跑，
不需要浏览器**。实测：

| 实现 | 耗时 | 峰值内存 |
|---|---|---|
| Playwright + Chromium | 3.78s | **959 MiB** |
| curl + Node | **2.89s** | **78 MiB** |

`__ac_signature` 确实被校验，且与 nonce 绑定——5 组反例（无签名 / 垃圾签名 /
空签名 / 无 nonce / 错配 nonce 的合法签名）全部拿不到身份。

**实测验证结果**（真实分享链接 `https://v.douyin.com/ik9FpufxgSE/`）：

- 短链展开 → `aweme_id=7658147082263416115`
- 签名 detail 请求 → `HTTP 200`，103687 字节完整 `aweme_detail`
- 解析出 **23 档清晰度**，最高 `3840x2160`
- 实际下载：`content-length=12578471` / `received=12578471`，`ftypisom` 真 MP4
- 同身份连发 10 次：**10/10 成功**，中位 304ms
- 身份有效期：`UIFID_TEMP` expires **2028-01**，`ttwid` **2027-09**

**`play_addr` 确认无水印**（抽帧肉眼比对）：

| 流 | 分辨率 | 水印 |
|---|---|---|
| `play_addr` | 1920×1080 | **无** |
| `download_addr` | 1280×720 | **有**（抖音 logo + `抖音号: <作者>` + 飘动 ID） |

因此主链路取 `play_addr`，`download_addr` 只在无其它源时才兜底。

#### (6) 一个必须先知道的风控事实：限流是 IP 维度的

复测中得到的最重要工程结论，**推翻了"多身份轮换可以提升吞吐"的直觉**：

- 触发点：约 **60 次 / 20 线程**并发 → `HTTP 444 Access Denied`
- 触发后：**在同一 IP 上铸一个全新身份，同样被拒**
- **真实 Chrome 也一样**：抓包显示浏览器发出的、带完整签名
  （`a_bogus` + `x-secsdk-web-signature` + `uifid` + `verifyFp`）的
  detail 请求，在同一时刻同样返回空响应
- 恢复：**无需换 IP、无需换身份**，实测约 **20 分钟**后自行恢复

而同一时刻，**未受保护的接口照样正常**（`hot/search/list` 返回 71KB）
——说明 IP 并没有被封死，只是受保护接口被降级。

另外，`UIFID_TEMP` 的 160 个字符里有 **96 个是跨铸造共享的前缀**
（由 IP/环境派生），只有后 64 字符随机——平台能轻易把多个身份关联成同一来源。

**工程含义**：

1. 证书池只能提供**韧性**（单证书失效时顶替），**不能提升吞吐**；
   要真正独立，必须配代理池（`netx.Options.Proxy` 已支持）。
2. 抖音的 host 限流应比全局值保守得多（实测安全线约 3~4 req/s）。
3. **必须把 `200 + 0 字节` 判为限流**，否则会被误判成成功。
   本项目已映射为 `KindRateLimit`。
4. **禁止并发铸造**：实测 3 个 Node 进程并发峰值 **295 MiB**，线性叠加。

### 1.6 风控要点

- 风控状态码：body 层 `{8, 2154, 2156, 10000, 10001}`；HTTP 层 `{401,403,405,412,429,444}`
- **三种响应要分清，它们的成因完全不同**：

  | 响应 | 含义 | 处理 |
  |---|---|---|
  | `403 Uifid Not Found` | Cookie 里**根本没有** `UIFID_TEMP` | 铸造一个身份 |
  | `444 Access Denied` | **IP 维度**限流（显式） | 退避，**不要换身份** |
  | **`200` + 0 字节** | **IP 维度**限流（静默） | 退避，**不要换身份** |

  最后一种最危险：只判断状态码会误判成成功。本项目映射为 `KindRateLimit`。
- **限流是 IP 维度的，换身份无效**（实测：限流窗口内新铸的身份同样被拒，
  真实 Chrome 同样被拒）。详见 1.5 节 (6)。
- **`msToken` 在抖音可以缺失/伪造**（实测：伪造 100827 字节、不带 101950 字节、
  矛盾 token 101833 字节，三者都返回完整 payload）——
  而在 TikTok 上伪造 token 会直接返回 0 字节。两个平台行为完全相反。
- **`s_v_web_id` 不是必需的**：实测 Cookie 里只有 `UIFID_TEMP` + `ttwid`
  （没有 `s_v_web_id`）时，签名同样被接受并返回完整数据。
- 受签名保护的端点清单（14 条，抄自抖音 SDK 的 `webSign.config.protectedHost`）：
  `aweme/detail/`、`aweme/post/` **受保护**；
  `user/profile/other/`、`comment/list/` **不受保护**
- 作品 ID 自校验：Snowflake 高 32 位是秒级时间戳，可据此拒绝明显非法的 ID，
  **在发请求之前**就失败
- **实测安全速率**：顺序无间隔（约 3.75 req/s）连发 30 次全部成功；
  20 线程并发 60 次触发限流。抖音的 host 限流应显著低于其它平台。

### 2.2 WBI 签名（已实测验证）

```python
mixin_key = reorder(img_key + sub_key, MIXIN_KEY_ENC_TAB)[:32]
query     = encodeURIComponent_sorted(params + {wts: now})
w_rid     = md5(query + mixin_key)
```

**Go 复现的三个关键坑**：

1. 必须用 `encodeURIComponent` 语义：空格 → `%20`（**不是** `+`），十六进制**大写**。
   Go 的 `url.QueryEscape` 把空格编码成 `+`，不能直接用。
2. 值的 `!'()*` 五个字符**先剔除**再编码。
3. `nav` 接口在未登录（`code=-101`）时**仍会返回** `wbi_img`，
   不能因为 `code != 0` 就跳过取 key。

实测结果（本机）：

```
img_key = 7cd084941338484aae1ad9425b84077c
sub_key = 4932caff0ff746eab6f01bf08b70ac45
mixin   = ea1db124af3c7062474693fa704f4ff8    ← 与官方文档示例完全一致
playurl → code=0，返回 6 条视频轨 + 3 条音频轨
```

### 2.3 fnval 位掩码（决定能拿到哪些流）

| 值 | 含义 |
|---|---|
| 1 | MP4 格式（仅 H.264） |
| 16 | DASH 格式 |
| 64 | HDR（仅 H.265，需 `qn=125`，大会员） |
| 128 | 4K（需 `qn=120` + `fourk=1`，大会员） |
| 256 | 杜比音频 |
| 512 | 杜比视界 |
| 1024 | 8K |
| 2048 | AV1 编码 |
| **4048** | **所有可用 DASH 流**（16\|64\|128\|256\|512\|1024\|2048） |

### 2.4 清晰度档位（qn）

`6`=240P / `16`=360P / `32`=480P / `64`=720P / `74`=720P60 /
`80`=1080P / `100`=智能修复 / `112`=1080P+ / `116`=1080P60 /
`120`=4K / `125`=HDR / `126`=杜比视界 / `127`=8K / `129`=HDR Vivid

**DASH 模式下 `qn` 无效**（DASH 会返回所有档位），
请求 `qn=127` 只是声明"我想要的最高档"。

实测（匿名，无 Cookie）：

| 调用方式 | 实得档位 |
|---|---|
| `x/player/playurl`（**非签名**）+ `try_look=1` | **1080P / 720P / 480P / 360P** |
| `x/player/wbi/playurl`（WBI 签名）+ 同样参数 | 只有 480P / 360P |
| 非签名但**不带** `try_look` | 只有 480P / 360P |

2026-09-14 用 6 条热门视频逐条对照，**6/6 复现**上面的差异。
关键参数是 **`try_look=1`（试看）与端点选择**，两者缺一不可。

**这不是试看片段**：对 1080P 流做 ffprobe 探测，时长 212.32s 对上接口
返回的 `timelength` 212393ms（官方时长 213s），是完整视频。

> ⚠️ 本项目曾因为**优先走 WBI 通道**而长期只拿到 480P。
> 症状很隐蔽——请求成功、有流、只是低一档，不报任何错。
> 现已改为**非签名通道优先，WBI 仅作兜底**。
`accept_quality` 显示该视频支持到 `112`(1080P+)，但需要登录 + 大会员。

### 2.5 WBI 与降级通道的实测对比

这是一个有工程价值的实测结果：

| 通道 | 结果 |
|---|---|
| `x/player/wbi/playurl`（带 WBI 签名） | `code=0`，6 条视频轨 |
| `x/player/playurl`（**不带**签名） | `code=0`，**12 条**视频轨 |

两者都可用。官方文档把旧端点标注为"旧链接"（删除线），但社区下载器
（yutto 2.3.1）至今仍在用不带签名的那条。

**本项目的处理**：主用 WBI 通道，遇到 `v_voucher` 风控信号时
**自动降级**到无签名通道。两条路参数完全一致，只是签名与路径不同。

### 2.6 关于水印

- **文档层面零说明**：全仓库 `grep 水印 docs/` 只命中与视频流无关的
  抽奖卡片图字段。
- **UP 主内嵌水印**：像素内容，去不掉。
- **服务端台标**：与取流通道相关（见 0.2）。

  否则会把几分钟的试看当成完整视频返回。

### 2.7 CDN 节点差异（2026-09 实测，影响"浏览器直连"）

同一个视频每次取流会拿到**不同的镜像节点**，它们的放行策略并不一致：

| 节点类型 | 实测响应 | 浏览器能否直连 |
|---|---|---|
| `*.mcdn.bilivideo.cn:8082` | `Access-Control-Allow-Origin: *`，无需 Referer/UA/Cookie（HTTP 206） | ✅ 可以 `fetch` 直取 |
| `*.upos-sz-*.bilivideo.com`（主 CDN） | 裸请求、只带 UA、只带 Referer **都是 403**；`UA + Referer` 同时带才 200 | ❌ 不能（见下表） |
| `*.edge.mountaintoys.cn`（P2P CDN） | 同上：`UA + Referer` 同时带才 200 | ❌ 不能 |

主 CDN 的 Referer 判定很严——**必须是平台自己的域名**：

| 请求头组合 | 状态码 |
|---|---|
| 无 Referer（UA 可有可无） | `403` |
| `Referer: http://127.0.0.1:8081/`（本页地址，浏览器自动带的那个） | `403` |
| `Referer: https://example.com/` | `403` |
| `Referer: https://www.bilibili.com/` + 浏览器 UA | `200` |

而 `Referer` 与 `User-Agent` 都是 Fetch 规范里的 **forbidden header**，
脚本无法设置，浏览器也不会把跨站请求的 Referer 伪装成 bilibili 域名。
结论：**"在浏览器里直接取 B 站流"只对部分节点成立**，
任何依赖它的方案都必须准备兜底——本项目的前端混流就是这样：
直连 → （失败若是 403 就直接上代理，网络类错误才换节点重试）→ `/v1/proxy`。
代理侧补的是 `links.headers` 里给出的 Referer 与 UA。

### 2.8 风控

| 错误码 | 含义 |
|---|---|
| `-352` | 风控校验失败（UA 或 wbi 参数不合法） |
| `-412` | 请求被拦截（IP 被风控） |
| `-688` | 地理区域限制 |
| `-689` | 版权限制 |

WBI 签名缺失/错误时返回的不是 403，而是 `data.v_voucher`——
**表现为"能通但拿不到数据"**，很容易误判为业务错误。

`wts` 时效窗口约 **60 秒**，因此：

- 必须做时钟同步（可以从响应 `Date` 头校准）
- 重试退避总时长必须远小于 60s，否则重试必然因签名过期而失败

其它要点：

- CDN 取流有 **Referer 防盗链**（必须在 `.bilibili.com` 域下），UA 不能为空
- 取流直链有效期 **120 分钟** —— 这直接决定了服务端缓存 TTL 的上限
- `buvid3` 缺失容易触发风控；`bili_ticket` 非必需但能降低风控概率
  （生成：`hmac_sha256("XgwSnGZ1p", "ts"+timestamp)` → `key_id=ec02`）

## 3. 快手

### 3.1 好消息：**零签名、零 Cookie**

跨仓库检索确认（parse-video / video-parser / 本项目）：

```
__NS_sig3  sig  clientid  kpn=KUAISHOU_VISION
graphql  visionVideoDetail  rest/wd/photo/info
→ 全部零命中
```

快手移动端作品页把完整数据内嵌在 `window.INIT_STATE` 里，
**不需要任何签名，也不需要任何 Cookie**。

### 3.2 跳转链是唯一的技巧

```
v.kuaishou.com/xxxxx
  →302→ www.kuaishou.com/short-video/{photoId}   ← 中间落地页（PC 版结构）
  →302→ .../fw/photo/{photoId}                    ← 目标页（移动版结构）
```

中间那跳返回的是 **PC 版页面，结构完全不同**。因此必须精确控制在哪一跳停下。

社区的判定规则是：**只在新地址路径匹配 `^/short-video/[^/]+/?$` 时继续跟随**，
否则停下。本项目实现为逐跳推进 + 路径判定。

另外 `/fw/long-video/` 的返回结构与 `/fw/photo/` 不同，需要统一改写路径。

### 3.3 数据提取

页面的顶层键是**动态的**（形如 `{"VisionVideoDetailPhoto:xxx": {...}}`），
所以不能按固定键取值。

鲁棒的定位方式是：**递归寻找"同时包含 `result` 与 `photo` 两个字段"的对象**。
这比猜键名可靠得多——前端改键名不受影响。

字段路径：

```
photo.caption                 标题
photo.mainMvUrls[0].url       视频（无水印）
photo.coverUrls[0].url        封面
photo.userName / headUrl      作者
photo.ext_params.atlas.cdn[0] + .list[]   图集（CDN 主机 + 相对路径拼接）
```

PC 版（`__APOLLO_STATE__`）对应：
`VisionVideoDetailPhoto:{id}.caption/.coverUrl` 与
`VisionVideoSetRepresentation:1.url`。

### 3.4 关于"高清排序"

参考实现都是直接取 `mainMvUrls[0]`，**没有任何清晰度比较分支**。
要真正选最高清，需要自己遍历 `manifest.adaptationSet[].representation[]`
（按 `bitrate` / `meta.height` 排序）——本项目已实现该路径。

### 4.1 两条链路，本项目走零签名的 HTML 路线

**HTML 链路（零签名）** — 本项目采用

```
GET https://www.xiaohongshu.com/explore/{noteId}?xsec_token=...&xsec_source=...
  → window.__INITIAL_STATE__ = {...}
  → note.noteDetailMap[{noteId}].note
```

**API 链路（需全套签名）**

```
POST https://edith.xiaohongshu.com/api/sns/web/v1/feed
  Headers: x-s, x-s-common, x-t, x-b3-traceid, x-xray-traceid, x-rap-param
  Cookies: a1, webId, web_session, gid, acw_tc, websectiga, sec_poison_id ...
```

### 4.2 `__INITIAL_STATE__` 的 `undefined` 坑（本项目已实测绕过）

这是小红书最经典的坑：内嵌的不是合法 JSON，而是 JS 对象字面量，
里面大量出现 `undefined`：

```javascript
window.__INITIAL_STATE__ = {"note":{"currentNoteId":"abc", "x": undefined, ...}}
```

- 用 **gjson** 这类宽松解析器：可以容忍
- 用 **`encoding/json`** 这类严格解析器：**直接报错**

本项目的 `jsonx.Sanitize` 会在解析前把独立的 `undefined` token 替换为 `null`，
并且**只在字符串字面量之外替换**（避免误伤内容里的 "undefined" 一词）。

实测：用一个不存在的 noteId 请求真实页面，解析链路成功走到
"未找到笔记数据"这一步——说明 HTML 抓取 → 正则提取 → undefined 容错 →
JSON 解析全链路都是通的。

另外 `noteId` 的字段名在不同版本里不一致（`currentNoteId` vs `firstNoteId`），
本项目按优先级多路尝试并兜底遍历。

### 4.3 无水印：四个平台里唯一需要**主动改写 URL** 的

**视频**：字段本身就是无水印源，直接取。

```
video.media.stream.h264[0].masterUrl     （也支持 h265 / av1）
video.consumer.originVideoKey            → https://sns-video-bd.xhscdn.com/{key}
```

**图片**：需要改写。这是全社区唯一一处真正的"去水印 URL 改写"：

```
原始： https://sns-webpic-qc.xhscdn.com/.../notes_pre_post/1040g2sg31xxx!nd_dft_wlteh_webp_3
改写： https://ci.xiaohongshu.com/notes_pre_post/1040g2sg31xxx?imageView2/format/jpg
```

改写规则：

1. 取路径最后一段，按 `!` 截断（`!` 之后是平台的处理参数）得到 `imgId`
2. 若原 URL 含 `spectrum`，新 URL 需要带 `spectrum/` 前缀
3. **若原 URL 不含 `notes_pre_post`，改写会失效，必须回退原地址**

第 3 条是实测得出的硬约束，不能省略。

### 4.4 签名算法（如需 API 链路）

社区实现（RedCrack）是 **100% Python 纯算法，不执行任何 JS**
（无 execjs / mini-racer / v8，也不下载 JS）。这意味着**理论上可以纯 Go 复刻**。

Go 复刻难度分级：

| 参数 | 难度 | 关键点 |
|---|---|---|
| `x-b3-traceid` `x-xray-traceid` `a1` `gid` | ★☆☆☆☆ | 简单随机/CRC32 |
| `x-s-common` | ★★☆☆☆ | 自定义 Base64 + RC4 |
| `x-s` | ★★★☆☆ | `"XYS_" + 魔改B64(...)`，内层 144 字节载荷 ⊕ XOR_KEY |
| `x-rap-param` | ★★★★☆ | 唯一非标准库难点：需**位级兼容 gzip（fflate）** |

关键事实：**`a1` 是本地算法构造的，不来自任何端点**；
**游客态可用**（自动调 `login/activate` 换 `web_session`）。

### 4.5 风控

| 状态 | 含义 |
|---|---|
| `461/471` + `Verifytype:124` | 需要扫码登录 |
| `102` | 滑块验证 |
| `406` | 风控拒绝 |
| 200 但 msg 含"登录已过期" | 登录态失效 |

## 6. 工程结论：如何"不写死"

平台页面和接口会变，因此本项目刻意避免把易变信息固化进代码：

| 易变项 | 本项目做法 |
|---|---|
| JSON 字段路径 | `jsonx.Pick(node, "pathA", "pathB", ...)` **多路径回退**，改版通常只需补一条候选 |
| 页面内嵌变量名 | `webx.ExtractWindowJSON(html, "候选1", "候选2")` + 通用 `window.X = {...}` 兜底 |
| 快手动态键名 | 按**结构特征**（同时含 `result` 与 `photo`）定位，而不是猜键名 |
| 接口地址 | 每个提取器都有 `Endpoints` 结构体，可覆盖，不散落在代码里 |
| 签名版本 | `abogus.Variant` **数据化**，并把已知矛盾固化成测试 |
| UA / Referer | `deps.Params` 集中管理，可运行期覆盖 |
| Cookie / 密钥 | **只用环境变量注入**，代码零硬编码 |
| 平台域名 | `Extractor.Hosts()` 由提取器自报，注册表自动索引 |

# vidlink 架构设计

> 目标：**极轻量 + 高并发 + 高效率**的多功能视频解析 API 服务器。
> 本文记录关键设计决策、取舍理由，以及尚未完成的部分。

---

## 1. 总体形态

```
                    ┌──────────────────────────────────────┐
   HTTP 请求  ────▶ │  server 中间件链                      │
                    │  Recovery→Log→CORS→限流→鉴权          │
                    └───────────────┬──────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────┐
                    │  service（业务编排）                   │
                    │  · 路由到平台提取器                    │
                    │  · TTL 缓存 + 请求合并(singleflight)   │
                    │  · 全局并发闸门 + 单次超时预算          │
                    │  · 批量并发编排                        │
                    └───────────────┬──────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
┌───────▼────────┐        ┌─────────▼─────────┐       ┌─────────▼────────┐
│ extract        │        │ sign              │       │ netx             │
│ Registry+4平台 │        │ sm3/abogus/wbi    │       │ 连接池/限流/重试  │
└───────┬────────┘        └───────────────────┘       └──────────────────┘
        │
┌───────▼────────────────────────────────────────────────────────────┐
│ 支撑层（全部零第三方依赖）                                          │
│ core(模型/接口) · jsonx(容错JSON) · webx(内嵌状态) · urlx(URL归一)  │
│ cache(泛型TTL+singleflight) · deps(依赖容器) · config(环境变量)      │
└────────────────────────────────────────────────────────────────────┘
```

### 依赖方向

严格单向，无环：

```
main → server → service → {extract, cache, deps} → {core, jsonx, webx, urlx, netx, sign}
```

`extract` 包只负责注册表，平台实现（`extract/<platform>`）**不反向依赖** `extract`——
这是通过把共享依赖放进 `deps` 叶子包实现的。这个约束保证了"新增平台不改服务层"。

## 2. 九个关键设计决策

### 决策 1：零第三方依赖，只用标准库

**选择**：`go.mod` 里没有任何 `require`。

**理由**：

- 「极轻量」的最强保证是**依赖树为空**。任何框架都会带来传递依赖、
  更大的二进制、更慢的编译、更多的供应链风险面。
- 原以为必需的三件事，标准库其实都能做：
  - **路由**：Go 1.22+ 的 `ServeMux` 已支持 `GET /api/v1/parse/{platform}/{id}`
    这样的方法与通配模式，不需要 gin/chi/echo。
  - **JSON**：`encoding/json` + 自写 40 行路径导航即可，不需要 gjson。
  - **HTML**：目标是 `<script>` 里的 JSON 段，正则比 DOM 解析器更鲁棒，不需要 goquery。
- 唯一"重"的部分（SM3、a_bogus、WBI）本来就是自研算法，第三方库也没有。

**代价**：需要自己实现 `jsonx`（约 300 行）和 `webx`（约 150 行）。
考虑到它们同时承担了"多路径回退"这一核心鲁棒性职责，这个投入是划算的。

**结果**：6.9 MB 二进制，毫秒级启动，无 CGO。

### 决策 2：数据面不代理视频字节

**选择**：API 默认只返回 CDN 直链。媒体代理 `/api/v1/proxy` 默认**关闭**。

**理由**：

- 解析服务的瓶颈应该是"上游 API 调用"，而不是"带宽"。
  一旦开始代理视频，单机吞吐立刻从"每秒数千次解析"降到"几个并发流"。
- 服务端不碰视频字节 ⇒ 内存占用与视频大小无关 ⇒ 可以用极小的实例扛很高的并发。

**代价**：浏览器里 `<video src="直链">` 会因为 Referer 防盗链 403。
因此提供**可选**的流式代理，并且：

- 默认关闭；
- 开启时强制要求域名白名单（否则启动报错）；
- 纯流式转发（32KB 缓冲），内存占用与文件大小无关；
- 原样透传 `Range`，支持播放器拖动进度条；
- **不跟随重定向**（防止用受信域名 302 绕过白名单）。

### 决策 3：缓存与请求合并必须在一起

**选择**：`cache.Cache[V]` 同时提供 TTL 缓存与 singleflight。

**理由**：

- 只有缓存没有合并：缓存击穿时仍会打出 N 个上游请求。
- 只有合并没有缓存：串行化的收益无法跨请求保持。

两者结合后，**同一视频的 N 个并发请求只会命中上游 1 次**。

**实现要点**：

- **16 分片**降低锁竞争（FNV-1a 哈希选片）。
- **惰性过期**：没有后台清理 goroutine，空闲时零 CPU 开销。
- **TTL 抖动**（默认 10%）：打散同时到期的键，避免"齐步走"式缓存雪崩。
- **失败也缓存**（`NegativeTTL`，默认 45s）：防止对已删除内容反复打上游。
- 合并的等待者**不受首个请求 ctx 取消影响**——一个客户端断开不应让其他客户端失败。

**TTL 取值的取舍**：

- 平台取流直链有效期有限（B 站文档明确写 **120 分钟**）；
- 元信息基本不变。
- 默认取 **10 分钟**：足够吸收热点流量，又不会返回临期链接。

### 决策 4：按主机限流，而不是全局限流

**选择**：`netx.Limiter` 是按 host 隔离的令牌桶。

**理由**：

- 各平台容忍度差异极大（B 站宽松、抖音风控严格）。全局桶会让慢平台拖垮快平台。
- 按主机隔离后可以各自调速，也可以针对触发风控的主机单独降速。

**实现**：惰性补充（lazy refill）而非后台 ticker——
高并发下没有定时器开销，空闲主机不占 CPU。

**另外还有一层**：`service` 里的**全局解析并发闸门**（信号量）。
它保护的不只是上游，也是自己——防止突发流量把所有 goroutine 都堆在等上游响应上。

### 决策 5：提取器可插拔，路由按域名索引

**选择**：`core.Extractor` 接口 + `extract.Registry` 注册表。

```go
type Extractor interface {
    Name() core.Platform
    Hosts() []string
    Match(u *core.URL) bool
    Parse(ctx context.Context, u *core.URL) (*core.Video, error)
}
```

**理由**：

- 服务层只依赖接口 ⇒ 新增平台不需要改服务层与路由层。
- 路由先按域名后缀缩小候选，再调 `Match` 做精细判断 ⇒
  不对每个请求逐个试错（N 个平台就是 N 次尝试）。
- 可选的 `ByIDExtractor` / `BatchExtractor` 用类型断言探测 ⇒
  平台按需实现，不强制。

**安全细节**：域名匹配用 `HostHasSuffix` 而不是 `strings.Contains`。
后者会把 `evil-bilibili.com` 误判为 `bilibili.com`，这是一个真实的跨站劫持隐患。

### 决策 6：多路径回退，而不是写死字段路径

**选择**：`jsonx.Pick(node, "pathA", "pathB", ...)` 按优先级取第一个非空值。

**理由**：平台响应结构会随前端发版而变（改驼峰/下划线、层级调整、
同名字段搬家）。写死单一路径的话，平台一改版整条链路就挂；
多路径回退通常只需补一条候选。

**配套手段**：

| 场景 | 手段 |
|---|---|
| 内嵌变量名会变 | `webx.ExtractWindowJSON(html, "候选1", "候选2")` + 通用 `window.X = {...}` 正则兜底 |
| 顶层键名完全动态（快手） | 按**结构特征**定位（递归找"同时含 `result` 与 `photo`"的对象），而不是猜键名 |
| 接口地址会变 | 每个提取器有 `Endpoints` 结构体，可覆盖 |
| 有的响应驼峰、有的下划线 | `Pick("baseUrl", "base_url")` 同时列上（B 站同一响应里两种键名并存） |

### 决策 7：签名算法数据化，而不是魔法常量

**背景**：调研中发现参考实现的 a_bogus **源码与它自己的黄金向量互相矛盾**
（模板第 34 号标志位，密文要用 `2`，校验和却要按 `3` 算）。

**选择**：把这个标志位做成 `abogus.Variant` **数据**，两个解释都保留：

```go
const (
    VariantSourceFaithful  // 照抄源码（自洽，但与黄金向量差 1 字符）
    VariantVectorFaithful  // 以黄金向量为准（默认）
)
```

并用测试把这个已知差异**固化**：

```go
func TestVariantSourceFaithfulDiffersByOneByte(t *testing.T) {
    // 断言差异"恰好 1 处"
    // → 一旦差异位置或数量变化，说明我们对模板的理解又变了，必须重新评估
}
```

同理，无法由 UA 推导的 32 字节指纹也做成可替换的 `Fingerprint`。

**为什么这样更好**：如果直接把某个值写死，将来线上失败时你无法判断
"是算法变了"还是"我抄错了"。把它数据化 + 测试固化后，**变化会显式暴露**。

### 决策 8：中间件顺序是**契约**，不是实现细节

**选择**：中间件从外到内的顺序被固定并写进注释，测试把它钉死：

```
Logging → RequestID → Recovery → CORS → RateLimit → APIKey → mux
```

**为什么这不是"随便排排"**：其中一条顺序错了会表现为**完全无关的症状**。

真实踩过的坑：最初把 `APIKey` 放在最外层，看起来更"安全"（先鉴权再干别的）。
但浏览器跨域预检（`OPTIONS`）按 Fetch 规范**不携带任何凭据**——它天然过不了鉴权。
于是预检被 403，浏览器判定跨域失败，**正式请求根本不会发出**。

症状是"一开启 API Key，网页端就完全用不了"，而服务端日志里只有一串
看不懂的 `OPTIONS 403`。从日志出发几乎不可能推断到"中间件顺序"这个原因。

**固化手段**：`TestCORSPreflightIsNotBlockedByAuth` 断言"不带凭据的预检必须
返回 204"。任何把 CORS 挪到鉴权之内的改动都会立刻把它撞红。

**同一个思路的另一处**：`X-Request-Id` 是由 `withRequestID` 提前写进**响应头**的，
`writeErrorBody` 再从响应头回读它放进错误体。这样每个写错误的地方都不必
额外接一个 `*http.Request` 参数，代价是引入一条隐式约束——
`withRequestID` 必须在所有处理器之外。它同样由 Handler() 的装配顺序保证。

### 决策 9：路由三者同源

**选择**：用一张 `routeSpec` 表声明路由，它同时服务三个消费者：
ServeMux 注册、鉴权豁免名单、以及"未匹配时给 404 还是 405"。

**理由**：这三件事本来会各自硬编码一份路径清单，结果是"加了新接口、
忘了加豁免"，症状是"探针突然开始 403"。

**顺带解决的一个 Go 细节**：`ServeMux` 只在**没有兜底模式**时才自动返回 405。
而我们既想要兜底（给出结构化 404 而不是裸的 `404 page not found`），
又想要正确的 405 —— 两者不可兼得。所以兜底自己实现：

| 情况 | 状态码 | 判据 |
|---|---|---|
| **路径**不存在 | 404 | 不匹配任何路由模板 |
| **方法**不对 | 405 + `Allow` | 路径匹配模板、方法不在允许集 |
| **参数取值**不对 | 400 | 路径匹配且方法正确，但参数值非法 |

最后一条是刻意的：`/api/v1/parse/weibo/123` 返回 **400 而不是 404**，
因为路径模板是匹配的，问题出在参数取值。把"路径写错"和"平台不支持"
用不同状态码分开，客户端才能自助排障。

## 3. 并发模型

```
                      ┌──────────────────────────────┐
   1000 个并发请求 ───▶ │ service.sem（全局闸门）        │
                      │ 容量 = max(16, batch*4)       │
                      └──────────────┬───────────────┘
                                     │
                      ┌──────────────▼───────────────┐
                      │ cache.GetOrLoad（singleflight）│
                      │ 同 key 只放行 1 个到下游        │
                      └──────────────┬───────────────┘
                                     │
                      ┌──────────────▼───────────────┐
                      │ netx.Limiter（按主机令牌桶）    │
                      │ 保护上游，防风控               │
                      └──────────────┬───────────────┘
                                     │
                      ┌──────────────▼───────────────┐
                      │ http.Transport 连接池          │
                      │ MaxIdleConnsPerHost=32        │
                      └──────────────────────────────┘
```

**四层防护各司其职**：

| 层 | 防的是什么 |
|---|---|
| 全局闸门 | 自己被打爆（goroutine/内存耗尽） |
| singleflight | 重复劳动（同一视频被并发解析） |
| 按主机限流 | 上游被我们打爆（触发风控/封 IP） |
| 连接池 | 连接建立开销（TCP/TLS 握手） |

**超时预算**：

- 单次解析 20s（`VIDLINK_PARSE_TIMEOUT`）
- 单次 HTTP 请求 12s（`VIDLINK_HTTP_TIMEOUT`）
- 重试 2 次，指数退避 + 抖动，**只对幂等请求与可重试状态码生效**
- 请求体缓冲：重试时用 `GetBody` 重放，避免"第二次重试时 body 已读完"

**一个刻意的设计**：解析的超时预算**独立于客户端 ctx**。
客户端断开不应让缓存里的加载半途而废（否则会产生"空缓存"抖动，
下一个客户端又要重新打上游）。

## 4. 错误处理

错误被分类为 8 种 `Kind`，中间件只需读 Kind 就能决定 HTTP 状态码，
不必解析错误字符串：

| Kind | HTTP | 含义 |
|---|---|---|
| `KindBadInput` | 400 | 输入不合法 |
| `KindUnsupport` | 400 | 不支持的链接/平台 |
| `KindNotFound` | 404 | 内容不存在/已删除 |
| `KindForbidden` | 403 | 需要登录态/Cookie 失效/区域限制 |
| `KindRateLimit` | 429 | 被限流 |
| `KindTimeout` | 504 | 上游超时 |
| `KindUpstream` | 502 | 上游异常 |
| `KindInternal` | 500 | 服务内部错误 |

**"部分成功"的表达**：`core.Video.Warning` 字段承载降级提示。
例如未配置 B 站 Cookie 时：

```json
"warning": "未配置 B 站 Cookie，本次最高只取到 720P；配置 SESSDATA 可能解锁更高清晰度"
```

这比"静默返回低清"或"直接报错"都好——用户知道发生了什么，也知道怎么改进。

**批量解析**：单条失败不影响其它条，每条独立返回结果或错误详情。

## 5. 性能特征

实测（本机，解析 B 站视频）：

| 场景 | 耗时 |
|---|---|
| 首次解析（走完 view + playurl 两次上游） | ~700 ms |
| 命中缓存 | ~1 ms |
| a_bogus 单次签名 | ~3–5 µs（纯计算，无 JS 引擎） |
| WBI 单次签名 | ~1 µs + 口令缓存（6h TTL） |

**签名器的并发设计**：`abogus.Signer` 与 `wbi.Manager` 都是
**无可变共享状态**的（随机源用 `math/rand/v2` 的无锁实现，
口令缓存用 `RWMutex` + 串行化刷新），因此可以被任意多个 goroutine 共享。

**缓存观测**：`/api/v1/stats` 暴露 `hits / misses / coalesced / loads`。
其中 `coalesced` 直接反映 singleflight 省下了多少上游请求。

## 6. 安全设计

| 风险面 | 措施 |
|---|---|
| 开放代理 | 媒体代理默认关闭；开启时强制白名单；不跟随重定向；只允许 GET/HEAD |
| 未授权访问 | `VIDLINK_API_KEYS` 非空时强制校验（Header / query / Bearer 三种方式） |
| 滥用 | 每 IP 令牌桶限流（惰性 GC，防止 IP map 无限增长） |
| 上游被刷 | 按主机限流 + 全局闸门 + 批量上限 |
| 域名劫持 | `HostHasSuffix` 精确后缀匹配，不用 `Contains` |
| 密钥泄漏 | Cookie/密钥只从环境变量读，代码零硬编码；日志不打印 Cookie |
| SSRF | 媒体代理白名单 + 拒绝非 http/https scheme + 不跟随重定向 |
| 请求体炸弹 | `http.MaxBytesReader` 限制批量请求体 1 MiB |
| 真实 IP 伪造 | 仅在配置 `VIDLINK_TRUSTED_PROXY_HEADER` 时才信任代理头 |

**启动时的安全提醒**：未配置 API Key 时打印 Warn 日志
（"接口处于无鉴权状态，请勿直接暴露到公网"）。

## 7. 尚未完成 / 演进路线

按优先级排列：

### P0 — 补齐平台能力

1. **B 站分 P 与番剧**
   当前只取第 1 P（`pages[0]`）。需要支持 `?p=N` 与
   `/bangumi/play/ep{id}`（`pgc/player/web/v2/playurl`）。
2. ~~B 站 TV 通道（无水印）~~ —— **已决策放弃**。
   经确认"平台下发水印"在 B 站及整个行业普遍存在，不值得为此引入
   TV 端 `access_token` 依赖。B 站清晰度优先，水印不做处理。
3. ~~抖音身份链路~~ —— **已完成**（2026-09-14 实网验证到字节级别）。
   三件套里只有 `UIFID_TEMP` 需要外部取得，且只需**铸造一次**（有效期到 2028-01）：

   | 件 | 实现位置 |
   |---|---|
   | `a_bogus` | `internal/sign/abogus`（现网接受现有老一代实现，**无需移植新算法**） |
   | `x-secsdk-web-signature` | `internal/sign/secsdk`（纯 MD5 + 公开盐） |
   | `timestamp` | `time.Now()` |
   | `UIFID_TEMP` | `tools/douyin-mint/mint-identity.sh`（curl + Node，**不用浏览器**；该脚本未随仓库发布） |

   **决策：不加 sidecar。** 铸造是一次性运维动作，产物是一个 Cookie 字符串，
   通过 `VIDLINK_COOKIE_DOUYIN` 注入即可——主进程保持纯 Go、零依赖。
   sidecar 只有在需要"服务自己续期"时才值得，而实测身份有效期以年计，
   收益不足以抵消一个常驻外部进程的成本。

   **新发现的硬约束**：限流是 **IP 维度**的，换身份无效（实测新铸身份同样被拒，
   真实 Chrome 同样被拒）。因此 `200 + 0 字节` 必须判为 `KindRateLimit`，
   且抖音的 host 限流要显著低于其它平台。详见 `docs/平台调研报告.md` 1.5 节 (6)。

   （会引入 `google.golang.org/protobuf` 依赖，与"零依赖"冲突，
   需要评估：手写 varint 解析约 200 行可保持零依赖）。
5. **小红书 API 链路**
   HTML 链路已可用。API 链路（`edith.xiaohongshu.com`）需要实现
   `x-s` / `x-s-common` / `x-rap-param` 签名。难度最高的是
   `x-rap-param` 里的 **fflate 位级兼容 gzip**。
6. **可选混流**
   当前只返回分离流 + `needs_mux` 提示。可以做成可选的服务端混流，
   但那会引入 ffmpeg 外部依赖，与"极轻量"冲突 —— 建议保持"只提示不代劳"。

### P2 — 工程化

7. ~~HTTP 服务化基础~~ —— **已完成**：CORS 预检顺序、404/405 语义、
   request id 贯穿、存活/就绪探针、限流响应头、OpenAPI 规格、
   Dockerfile/Makefile/CI。均有回归测试。
8. **可观测性**：Prometheus metrics 端点（目前只有 JSON 统计与结构化日志）
9. **Cookie/身份健康检查**：定期验证 Cookie 有效性，失效时告警
10. **限流自适应**：根据上游错误率动态降速（当前是静态配置）
11. **测试覆盖**：签名算法有权威向量可验证、HTTP 层已有回归测试；
    提取器仍缺基于 HTTP mock 的解析测试（目前只靠实网联调）。
12. **按 Key 计量与配额**：当前限流按 IP。作为付费服务需要按 API Key
    计量、分档配额、用量查询。这是商业化前必须补的一块。

### 明确**不做**的事

- **不做图像处理去水印**。平台的干净流已经存在，我们只是选择它。
  UP 主压进画面的水印是像素内容，去不掉也不应该去。
- **不绕过付费/会员/版权限制**。遇到 `-688`（地区限制）等错误原样透传。
- **不做"试看片段"的伪装**。必须做时长交叉校验，如实标注。
